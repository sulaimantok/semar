# Security review: v0.1.0 (Phase 1)

The roadmap requires a security review before every `v0.x` release that adds a sensitive surface. For v0.1.0 that surface is **provider credentials**, the **console proxy** and **authorization**. This review covers the code on the Phase 1 branch; anything that still needs a real OpenStack or Proxmox lab is listed under [Open items](#open-items).

Method: the code paths below were read against the attack classes of a web API with a WebSocket proxy (authentication and session handling, CSRF and cross-site WebSocket hijacking, authorization and data isolation, secrets handling, SSRF and outbound requests, injection, resource exhaustion, supply chain). Each claim marked *tested* has an automated test; *verified* means it was also exercised end to end against running binaries.

## Fixed during the review

| # | Finding | Impact | Fix |
|---|---|---|---|
| 1 | Provider HTTP clients followed redirects. Go drops `Authorization` on cross-host redirects but forwards custom headers, so OpenStack's `X-Auth-Token` would be sent to whatever host a redirect named. | A redirecting (misconfigured or compromised) endpoint could collect a Keystone token. | Provider clients and the console dialer follow redirects only within the same scheme and host (Nova redirects `/v2.1` to `/v2.1/`); anything else is refused (`httpx.ErrRedirect`). *Tested*: a cross-host target receives no token. |
| 2 | Open consoles were unbounded. | One user could exhaust connections and goroutines with many consoles. | At most 5 open consoles per user and 200 per process; more are refused with 429. *Tested*. |

Found and fixed earlier in Phase 1 (recorded here for completeness):

| Finding | Fix |
|---|---|
| TLS pinning in `VerifyPeerCertificate` is skipped on resumed TLS sessions. | The pin is checked in `VerifyConnection`, which also runs on resumption. |
| The dev/preview proxy rewrote `Host`, so the CSRF Origin check refused every POST, and a proxy that rewrites Host in production would do the same. | The proxy keeps `Host`; `SEMAR_TRUSTED_ORIGINS` covers reverse proxies. |
| Login had no rate limit, and argon2id (64 MiB per hash) had no concurrency bound. | Per-IP and per-username limits; at most 4 concurrent hashes. |
| The owner of the audit table, not only a superuser, can disable its triggers. | Services run as a role that owns nothing; `semar-api migrate` runs as the owner (database roles runbook, *verified*). |
| Driver error text (hosts, URLs) reached clients and the audit log. | Clients and the audit log get a classification only; details are logged. |
| A restore started with the wrong KEK made connection checks fail with a bare 500. | Undecryptable credentials are reported as such (503 naming `SEMAR_KEK`; the sync status says why). Found while testing the backup runbook. |

## Checked and found sound

**Authentication and sessions**
- Session tokens are random, stored only as hashes, sent as HttpOnly, SameSite=Strict cookies (Secure by default). Login failures are uniform in message and timing.
- Every operation has an access policy; operations without one are refused. A test fails when a new operation is added without one, and the authorization matrix runs every operation against every kind of caller (*tested*).

**CSRF and cross-site WebSocket hijacking**
- State-changing requests need `X-Requested-By` and a same-origin (or trusted) `Origin`.
- The console WebSocket checks `Origin` with the same rule **before** upgrading; a missing Origin is refused (*verified*: foreign Origin answered 403).

**Console proxy**
- Tokens are single-use, valid for 30 seconds, stored as hashes, and bound to the user, the login session and the VM. A token presented from another session, reused, or expired is refused without telling the cases apart (*tested*, *verified*).
- The token travels as a WebSocket subprotocol, never in a URL; the server answers with `binary` only (*verified*: the token is absent from API and proxy logs).
- Provider URLs, tickets and VNC passwords stay on the server. For Proxmox, SEMAR answers the RFB VNC authentication itself and offers the browser no authentication, so the ticket that doubles as the VNC password never reaches the browser (*tested*, *verified* against a VNC server that requires the password).
- Consoles need an Admin or Operator binding covering the VM; viewers get 403, callers who cannot see the VM 404. Sessions end on idle timeout, maximum duration, or when a re-check every minute finds the login session or the role gone (*tested*).
- Every console is audited: token issued, opened, closed (reason, duration, bytes).

**Authorization and data isolation**
- Visibility is applied in SQL by one shared predicate for lists, aggregates (capacity) and details; aggregates never count resources a caller could not list (*tested*).
- Details of resources outside the caller's scope answer the same 404 as missing ones.
- Sync status hides driver error text from non-admins.

**Secrets**
- Provider credentials use envelope encryption (a data key per secret, AAD bound to the row, versioned KEK, online rewrap). No endpoint returns a secret; secrets never appear in audit details, logs or Temporal payloads (the worker decrypts inside the activity).
- Decrypted secrets are cleared after use where Go allows it; drivers keep the fields they need.
- The audit webhook is configured by the operator only (no SSRF from users) and signs deliveries with HMAC-SHA256.

**Injection**
- SQL is assembled only from placeholders and fixed fragments; all values are bound parameters.
- Provider data (VM names, tags, error text) is rendered by React as text. The serial console renders terminal output in xterm.js without link handlers.

**Resource limits**
- Request bodies are capped at 1 MiB; console messages from the browser at 1 MiB; provider responses at 64 MiB.
- Parallel provider calls (Placement, guest agents, disk configs) are bounded.

**Supply chain**
- New dependencies in Phase 1: `github.com/coder/websocket` (Go), `@novnc/novnc`, `@xterm/xterm`, `@xterm/addon-fit` (web). The console libraries are loaded only on the console page.

## Accepted risks

| Risk | Why accepted | Mitigation |
|---|---|---|
| The console connects to the URL Nova returns. | SEMAR already trusts the provider it manages; a compromised Nova could point SEMAR at another host. | No credentials are sent beyond the Origin header; redirects are refused. |
| Revoking a role or ending a session closes an open console within a minute, not instantly. | The re-check runs every minute. | Logout and role changes are audited; the maximum duration bounds any session. |
| Login rate limits are per process (roadmap R17). | Several replicas multiply the allowed rate. | The bound per replica still holds; a shared limiter belongs with the Full profile. |
| The metrics listener has no authentication. | It is separate from the API so it can bind to an internal interface. | Labels never carry secrets or raw paths. |
| The Lite profile uses one database role and an unauthenticated Temporal UI. | Lite is for development, bound to 127.0.0.1. | Production follows the database roles runbook; Temporal UI behind OIDC or not deployed (Phase 2). |
| Fake providers can be registered in any deployment. | They are needed for demos and tests. | Their console server listens on loopback only and serves generated data. |
